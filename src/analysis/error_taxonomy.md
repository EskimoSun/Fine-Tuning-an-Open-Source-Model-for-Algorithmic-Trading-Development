- Clean means the backtest finished, not that it traded. Clean runs with zero orders: Tuned 4B 2 of 13; Tuned 9B 3 of 15.

## 3. Jared's claim: is nearly half of the tuned runtime errors a missing resolution?

| Run | Runtime errors | `RESOLUTION_POSITIONAL` | Share of runtime errors | Static rule hits (whole source) |
|---|---:|---:|---:|---:|
| Base 9B (untuned) | 49 | 0 | 0% | 0 |
| Tuned 4B | 83 | 19 | 23% | 21 |
| Tuned 9B | 80 | 20 | 25% | 22 |

**Not confirmed at "nearly half". It is about a quarter:** Tuned 4B 19 of 83 runtime errors (23%), Tuned 9B 20 of 80 runtime errors (25%). It is still the largest single, exactly repeatable error in both tuned runs.

Three corrections to how the error is described:

1. **The resolution is not missing, it is misplaced.** In all 39 cases the model did pass `Resolution.X`; it put it in the positional slot that belongs to the moving-average type. QuantConnect's message is the same every time: `Argument mismatch: argument 3 ('moving_average_type') expected MovingAverageType, got Resolution.` (argument 4 for `bb`, argument 3 `'type'` for `atr`).
2. **It only happens on three indicators, so it only appears in three templates** (rsi-overbought-oversold, bollinger-mean-reversion, atr-volatility-stop). Inside those templates it is most of the failures: Tuned 4B 19 of 26 runtime errors (73%), Tuned 9B 20 of 29 runtime errors (69%). Outside them it is zero.
3. **The training data does not contain the wrong pattern.** In the 89 training templates, `self.rsi(` appears 0 times, `self.bb(` 1 and `self.atr(` 3, all in the correct form, and 0 of 1362 fine-tuning examples contain the wrong form. What the training data does contain is 25 other indicator calls that end in a positional `Resolution.X` (`self.ema(symbol, 20, Resolution.DAILY)`, `self.roc(...)`, and so on), which is valid for those indicators. My reading (an inference, not something the records prove): the model learned "resolution goes last" and applies it to indicators it rarely or never saw. That is under-coverage rather than memorising a bad example, and it means the fix is to add correct rsi / bb / atr examples, not to remove anything.

Supporting checks:

- The static rule (AST check for `Resolution.X` in that slot) finds the pattern in Tuned 4B 21 outputs, Tuned 9B 22 outputs. It catches every runtime hit (0 missed) and flags 0 clean backtests. The extra hits are outputs that crashed on an earlier line first: Tuned 4B atr-volatility-stop_v01, atr-volatility-stop_v05, Tuned 9B atr-volatility-stop_v01, rsi-overbought-oversold_v05.
- Fixing this line does not guarantee a clean backtest. The backtest stops here, so what would fail next in these 39 outputs is unknown.
- Read literally (no resolution given at all), the claim matches a different, non-crashing pattern: Tuned 4B 28 outputs, Tuned 9B 38 outputs call `add_equity` with no resolution. That never raises an error (the Bollinger reference template does the same), so it cannot explain any runtime-error count; where the prompt asks for hourly or daily bars it is a fidelity problem instead.
